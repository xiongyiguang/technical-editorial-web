# 页面原型、章节配方与组件调用规则

## 1. 三层模型

生成页面时按以下顺序工作：

1. **页面原型**回答“读者要完成什么任务”。
2. **章节配方**回答“哪些信息必须相邻、先后如何安排”。
3. **基础组件**回答“局部信息用什么视觉语法表达”。

禁止从组件库反向拼页面。先定任务和信息关系，再选组件。

## 2. 首页原型

| 首页原型 | 适用任务 | 必需信息 | 可选对侧 | 不应出现 |
|---|---|---|---|---|
| `thesis-proof` | 解决方案、倡议、投标概述 | 一句结论、对象、范围、证据状态 | 三条范围/证据摘要 | 无真实分类的标签行、虚构 KPI |
| `decision-data` | 管理报告、阶段评审 | 决策结论、报告期、数据口径 | 3–5 个已定义指标或状态 | 没有来源的数字、装饰图表 |
| `architecture-boundary` | 技术白皮书、架构说明 | 问题、边界、适用范围、版本 | 最高层真实链路或信任边界 | 产品口号式大图 |
| `evidence-media` | 项目案例、成果展示 | 案例结论、范围、资料状态 | 已批准主图、界面或成果证据 | 通用插画替代真实证据 |
| `plan-handoff` | 实施计划、交接计划 | 目标、固定约束、交付对象 | 工期/影响面/开关/表等摘要 | 没有依据的日期和工作量 |
| `mechanism-path` | 功能/概念解释 | 一段 TL;DR、文件或来源范围 | 请求路径、机制图或可调模型 | 与机制无关的品牌陈述 |
| `editor-task` | 分诊、配置、模板调优 | 要完成的动作、结果去向 | 状态、警告、导出动作 | 长篇营销式 hero |

首页必须从上表选择一个主原型。除非内容确有分类、筛选或状态集合，否则不要使用 topic chips。

## 3. 章节配方

### 3.1 `direction-comparison`

任务上下文块 → 2–4 个同源方向 → 固定比较维度 → 适用条件 → 推荐或选择结果。

- 每个方向必须使用同一份事实输入。
- 方向差异应来自结构、密度、阅读路径或交互，不只是颜色。
- 适用组件：`.context-panel`、`.comparison`、`.specimen-grid`、`.handoff-bar`。

### 3.2 `annotated-review`

审查对象与版本 → 风险地图/文件索引 → 原文或差异 → 邻近批注 → 结论与修正清单。

- 批注必须紧邻证据；严重性要有文本标签。
- 适用组件：`.summary-strip`、`.annotated-panel`、`.risk-ledger`、`.question-list`。

### 3.3 `mechanism-explainer`

TL;DR → 总路径 → 分步解释 → 可展开证据/代码 → 注意事项 → FAQ/术语。

- 稳定说明必须在无 JavaScript 时仍可阅读。
- 适用组件：`.mechanism-path`、`.code-tour`、`.context-panel`、`.faq-list`、`.glossary-grid`。

### 3.4 `reference-sheet`

用途和来源 → token/规则 → 分类样张 → 每项适用说明 → 导出或引用方式。

- 参考页可以密集，但必须有分类和一致标注。
- 适用组件：`.specimen-grid`、`.token-strip`、`.control-strip`。

### 3.5 `prototype-sandbox`

要验证的感受/行为 → 可操作原型 → 少量参数 → 行为解释 → 有意省略 → 开放问题。

- 只验证一个主要交互；提供复位和键盘路径。
- 适用组件：`.control-strip`、`.prototype-stage`、`.question-list`。

### 3.6 `status-report`

报告期与责任 → 摘要条 → 亮点/异常 → 明细表或趋势 → Carryover → 来源。

- 摘要条只放有定义、有周期、有来源的信息。
- 适用组件：`.summary-strip`、`.decision-grid`、图表、`.evidence-rail`。

### 3.7 `incident-report`

事件状态 → TL;DR → 时间线 → 根因 → 影响 → 行动项和责任。

- 时间轴只表达有时间顺序的事实；推断与事实分开。
- 适用组件：`.summary-strip`、`.milestone-rail`、`.risk-ledger`、`.decision-grid`。

### 3.8 `implementation-plan`

任务说明 → 交付摘要 → 里程碑 → 数据/责任流 → mockup → 关键实现 → 风险 → 开放问题。

- 每个里程碑同时写输出、负责人或范围标签、验收门。
- 适用组件：`.context-panel`、`.summary-strip`、`.milestone-rail`、`.mockup-pair`、`.code-tour`、`.risk-ledger`、`.question-list`。

### 3.9 `custom-editor`

编辑任务 → 输入/对象 → 约束和警告 → 实时或差异预览 → 可复核导出 → 复位。

- 浏览器状态不是最终事实；必须能生成文本或差异交接。
- 适用组件：`.editor-shell`、`.control-strip`、`.validation-note`、`.handoff-bar`。

## 4. 基础组件职责

| 组件 | 信息职责 | 使用门槛 |
|---|---|---|
| `.context-panel` | 显示任务、Prompt、来源边界或阅读说明 | 这段内容确实控制后续解释 |
| `.summary-strip` | 让读者在一行看到 3–5 个定义明确的事实或状态 | 每项有定义；数字需口径/周期/来源 |
| `.milestone-rail` | 表达时间、阶段或事件的顺序与确认节点 | 顺序真实且不可任意交换 |
| `.annotated-panel` | 将原文/图/代码与批注绑定 | 批注能定位到具体证据 |
| `.specimen-grid` | 展示同类组件、图形或方向样张 | 对象独立且比较维度稳定 |
| `.control-strip` | 调整少量影响结果的参数 | 参数真实改变结果或判断 |
| `.code-tour` | 按文件/步骤解释关键实现 | 代码或配置是论证证据 |
| `.mockup-pair` | 并列说明两个界面表面或状态 | 两者必须共同决定方案理解 |
| `.risk-ledger` | 对齐风险、级别、影响、责任和缓解 | 风险不是空泛注意事项 |
| `.question-list` | 收束未决问题、建议倾向与决策时点 | 问题会影响范围、实现或验收 |
| `.handoff-bar` | 输出下一动作、导出结果或交接对象 | 页面确有明确后续动作 |
| `.topic-chip` | 分类、筛选或状态集合 | 标签和数量来自真实内容 |

## 5. 组合约束

- 一页通常选择 1 个首页原型、1 个主章节配方、0–2 个辅助配方。
- 制作前先列出“章节—信息关系—展现形式—选择理由”清单。形式数量由真实内容决定，不设最低配额。
- 同类比较、证据或核验可以连续复用同一结构；若后续章节的信息关系不同，改用更合适的开放排版、表格、时间轴、图或证据栏。
- 四阶段、里程碑、上线批次、事件顺序和验收节点优先使用 `.roadmap` 或 `.milestone-rail`；表格只用于字段稳定、需要逐行核对的比较、接口或审计记录。
- 表格或矩阵数量服从稳定字段和逐行核对任务；不为减少表格数量丢失对比维度，也不用表格替代真实流程、分支或依赖关系。
- 背景用于区分信息分组或关键转折，不按章节数量轮换颜色。连续白底成立；确有结论支撑时可使用一个紧凑深色强调区。
- 图文模块制作前记录“图片数量、横竖比例、主次关系、共用或独立图注”四项。三张等权横图共证一个结论时用三联图；独立竖图各自成故事时用竖图卡片；正文为主、单图为证据时用紧凑图文横排；一主多辅时用主次拼图。
- 同一页面不连续复用同一种图文构图，除非它们属于需要保持一致的对比系列。变化来自内容关系和图片几何，不采用随机轮换。
- 组件不是越多越好。删掉没有真实信息职责的模块，页面会更清晰。
- 复用的是结构原则和语义类，不是固定文案、固定数量、固定配色或固定首页。
- 输出前检查首屏是否呈现当前材料的核心判断、证据或机制。真实闭环、枢纽、边界、渠道路径或分层关系可用图解释；结论和证据更清楚时采用文本或证据摘要，不强制添加图，也不要求不同任务一定改变两个构图特征。
- 中文交付物的可见眉题、章节标签、状态名、图题和动作名全部使用中文。仅官方产品名、源材料术语、代码标识或用户明确要求的双语内容保留英文。
