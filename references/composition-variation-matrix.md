# 构图变体矩阵

在选择页面模板后、编写 HTML 前使用本参考。目标不是随机换皮，而是让同一种信息关系拥有多个合适的视觉解法，并避免相邻章节和同批页面机械复用同一构图。

## 先做内容判型

为每个主要内容块标注一种主关系：

- 单论点：一个必须被记住的判断，其他内容只负责解释或举证。
- 并列多项：多个对象相互独立、权重相近，可以逐项扫描。
- 总分多项：一个总纲、平台或原则统领多个分支。
- 时间线多项：阶段、事件、批次、进入条件或验收节点存在真实先后关系。
- 循环闭环：输出回流为下一轮输入，或存在持续治理与反馈。
- 对比取舍：两个或多个对象需要按相同维度比较差异。
- 因果证据：事实、原因、影响、回应或结果构成可追溯链条。
- 分支决策：不同条件会进入不同路径或产生不同结果。
- 职责协同：同一流程跨越多个角色、部门或系统责任域。
- 范围边界：需要区分核心、纳入、依赖、排除和待确认内容。
- 状态成熟度：对象处于不同状态、级别、风险或承诺阶段。
- 数量关系：重点在大小、趋势、构成、差值或转化关系。
- 依赖网络：上游、核心、下游、外部系统或基础条件相互依赖。

一个内容块只选一个主关系。若同时具备多种关系，先选择最影响读者理解或决策的关系，次要关系放入注释、证据栏或后续章节。图片数量、横竖比例、主次和图注独立性属于媒介构图维度，继续按 `layout-modules.md` 的图文路由选择，不替代内容判型。

## 结构先行，内容可替换

HTML 生成后，改字通常容易，重建构图、连接关系和移动端顺序成本更高。因此按以下顺序制作：

1. 先列出章节、主关系、所选变体、阅读轴和背景节奏，不先写满正文。
2. 先完成低文字量骨架，确认主次宽度、连接方向、对象数量和桌面／移动顺序。
3. 用短标题、长标题、短段落、长段落和不同条目数量测试结构韧性。
4. 骨架通过后再填正式文字、证据、状态和来源。
5. 后续仅修改文字时，应保持模块、关系类和 CSS 不变；只有信息关系改变时才更换构图。

丰富呈现指信息几何真正不同，例如横向推进、纵向里程碑、中心辐射、条件分支、角色泳道、上下游依赖、开放条目和全宽论点。换颜色、换圆角、换图标或把三列改成四列不算新的呈现形式。

## 十三类内容的可选构图

| 内容关系 | 变体一 | 变体二 | 变体三 | 选择依据 |
|---|---|---|---|---|
| 单论点 | 证据分栏 `.split-layout` | 全宽结论带 `.thesis-band` | 批注式论点 `.single-point.is-annotated` | 连续解释用分栏；会议停顿用结论带；有多个限定条件时用批注式。 |
| 并列多项 | 开放式条目 `.ruled-list` | 结构化对象 `.showcase-grid` | 主次簇群 `.parallel-cluster` | 连续文字用条目；独立对象用结构化对象；存在重点项时用主次簇群。 |
| 总分多项 | 中心辐射 `.hub-map` | 总纲分支 `.hierarchy-branches` | 分层堆叠 `.architecture` | 共享中心用辐射；原则统领职责用分支；技术层级用分层。 |
| 时间线多项 | 横向路线图 `.roadmap` | 纵向里程碑 `.milestone-rail` | 错落事件线 `.timeline` | 阶段与确认节点用路线图；输出密集或移动优先用里程碑；事件回顾用事件线。 |
| 循环闭环 | 机制签名图 `.signature-visual` | 环形闭环 `.cycle-orbit` | 分段回流 `.cycle-loop` | 页面主机制用签名图；角色围绕共同核心用环形；线性步骤完成后回到起点用分段回流。 |
| 对比取舍 | 前后对比 `.comparison` | 方向比较 `.direction-grid` | 决策台账 `.decision-grid` | 两种稳定状态用前后对比；多个方案方向用同维度比较；需要责任和结论时用决策台账。 |
| 因果证据 | 事实影响回应 `.evidence-chain` | 难点方法结果 `.case-narrative` | 指标故事 `.metric-story` | 外部依据用证据链；项目复盘用案例叙事；主指标及驱动因素用指标故事。 |
| 分支决策 | 条件决策树 `.decision-tree` | 问题清单 `.question-list` | 机制路径 `.mechanism-path` | 条件决定路径时用决策树；尚未决策时用问题清单；系统内部路由用机制路径。 |
| 职责协同 | 职责泳道 `.swimlane-flow` | 流程链 `.process-chain` | 责任台账 `.risk-ledger` | 跨角色交接用泳道；单一主责任链用流程；需逐项审计责任时用台账。 |
| 范围边界 | 核心边界图 `.scope-map` | 内容成熟度 `.maturity-register` | 系统总体架构 `.system-architecture` | 项目纳入与排除用边界图；承诺边界用成熟度；系统及外部边界用总体架构。 |
| 状态成熟度 | 成熟度登记 `.maturity-register` | 风险台账 `.risk-ledger` | 摘要状态条 `.summary-strip` | 多状态对象用登记；风险责任需要逐行核对用台账；少量关键状态用摘要条。 |
| 数量关系 | 指标故事 `.metric-story` | 条形或趋势图 `.chart-figure` | 瀑布变化 `.waterfall-chart` | 单个主指标用故事；大小或趋势用图表；起点、增减和终点用瀑布。 |
| 依赖网络 | 依赖关系图 `.dependency-map` | 中心辐射 `.hub-map` | 系统总体架构 `.system-architecture` | 上下游依赖用关系图；共同服务中心用辐射；多层系统及治理依赖用总体架构。 |

## 变化约束

1. 相邻两个主要章节不得使用相同变体；连续三个章节不得使用同一构图家族。
2. 同一批交付中，稳定模板的 `data-composition-profile` 必须保持唯一。
3. 变化必须由权重、顺序、共享关系、证据密度、责任、条件或反馈方向驱动，不按页码轮换样式。
4. 长页至少使用四种有意义的表现形式，短页至少三种；颜色、圆角、图标或列数变化不计为构图变化。
5. 表格只服务稳定字段的密集比较、接口契约或审计台账，不得替代时间线、闭环、总分、分支、职责或依赖关系。
6. 不把流程和时间线混为一类：流程强调处理与交接，时间线强调日期、阶段、批次、进入条件或验收节点。
7. 不把总分和依赖混为一类：总分强调统领关系，依赖强调输入、输出、前置条件及影响传播。
8. 移动端可以改变空间方向，但必须保留原关系：先总后分、条件后分支、角色后动作、上游后下游、闭环有回流。

## 模板画像

每个稳定模板在 `<body>` 上声明唯一的 `data-composition-profile`。画像表达默认叙事侧重，不是固定页面清单：

- 方案：中心能力、业务链路、范围边界、路线图。
- 管理报告：数据结论、因果证据、决策台账、行动次序。
- 技术白皮书：分层边界、依赖网络、技术链路、控制证据。
- 项目案例：媒体证据、难点方法结果、交付对象、成果对比。
- 实施计划：里程碑、职责泳道、依赖、风险和开放问题。
- 技术解释：请求路径、分支决策、逐点批注、代码或证据走读。
- 工作台：分别保持缺口登记、方向比较、问题决策、机制检查和参数调整的独立构图。

画像之间不可仅靠标题、颜色或客户名称区分。

## 交付前检查

- 列出每个主要章节的主关系、所用变体和选择理由。
- 检查同一变体是否连续出现，检查卡片或表格语法是否超过两个主要章节。
- 检查流程与时间、总分与依赖、状态与边界是否被误判。
- 检查条件分支、职责交接、依赖方向、时间顺序和闭环回流是否具有明确文字标识。
- 检查替换标题、段落、状态和条目数量时是否仍能保持结构；若仅改字就需要重写 CSS，说明模块韧性不足。
- 检查桌面端与移动端的逻辑阅读顺序、连接线和中文标签。
