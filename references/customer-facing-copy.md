# 客户可见文案规范

在完成章节骨架后、填充正式文字前使用本规范。目标是让页面呈现客户结论、建设对象、业务价值、实施动作和确认事项，不暴露作者的写作过程、证据操作或内部方法论。

## 一、先区分两类文字

### 客户可见正文

包括导航、眉题、章节标签、章节标题、图题、卡片标题、状态名、说明文字和收束行动。它们必须直接回答以下至少一个问题：

- 要建设、治理、连接或改善什么；
- 这项设计为客户带来什么价值；
- 方案由哪些对象、关系或阶段构成；
- 当前需要确认什么、满足什么条件或采取什么行动；
- 事实、范围与承诺处于什么状态。

### 制作说明

包括“如何表达、如何使用资料、如何控制承诺、为什么选择某种版式”等生成过程说明。制作说明只能保留在技能文档、HTML 注释、工作台提示或交付前检查中，不得作为正式页面标题。

## 二、标题写法

标题优先使用以下四种结构：

1. **客户结论**：`统一客户资产与运营流程，形成可复盘的服务闭环`
2. **建设对象**：`统一客户运营平台与共享能力`
3. **业务价值**：`聚焦五类核心场景，明确试点优先级`
4. **行动方向**：`联合确认一期范围与启动条件`

禁止把制作动作写成标题，例如：

- `把建议能力与一期承诺分开表达`
- `外部事实只用于形成有边界的设计启示`
- `五类场景先确认价值与可实施条件`
- `用真实任务形成决策证据`

对应的客户化表达可以是：

- `平台能力分层规划，一期范围联合确认`
- `结合行业演进与合规要求，明确平台设计重点`
- `聚焦五类核心场景，明确试点优先级`
- `通过首批场景验证建设成效与推广条件`

## 三、避免内部黑话和生硬直译

客户可见栏目不得直接使用下列内部表达，除非源材料明确采用且客户熟悉：

| 不直接使用 | 按实际含义改写 |
|---|---|
| 决策门 / Decision Gate | 阶段确认、进入条件、验收节点、待确认事项 |
| Scope maturity | 范围状态、能力纳入状态、一期范围 |
| Validation gates | 验证安排、验收节点、推广条件 |
| Next action | 下一步、共同确认、后续安排 |
| Gotchas | 注意事项、关键边界、容易误解的问题 |
| Evidence scope | 依据范围、资料范围、结论依据 |
| Handoff | 交接安排、确认结果、输出说明 |
| Guardrail | 约束条件、安全边界、控制要求 |

同一个术语不得机械替换为固定中文。先判断它在当前内容中承担的是审批、准入、验收、范围还是行动职责，再选择自然表达。

## 四、范围与证据边界要写得自然

范围限制必须保留，但不要占据主标题，也不要连续使用防御性句式。优先使用“用途 + 项目落点”的正向结构：

- 生硬：`公开资料说明行业供给、接口约束、合规要求和智能化趋势，不替代广东移动本项目的调研结论。`
- 建议：`公开资料用于研判行业演进、接口边界、合规要求和智能化方向；本项目范围及实施方案仍需结合广东移动现状调研共同确定。`

- 生硬：`只呈现材料支持的能力，不加入自动诊断承诺。`
- 建议：`本节呈现材料已支持的建设能力；自动诊断能力纳入后续评估范围。`

减少连续使用“只用于、不替代、先确认、分开表达、不冒充”等自我辩护式词语。确需说明限制时，将其放在章节说明、来源注、状态标签或范围栏中。

## 五、章节编号与标签

- 正式方案、报告、白皮书、案例、实施计划和技术解释的普通一级主题章节使用 `01／02／03…` 连续编号，形成稳定的文档结构和会议节奏。
- 章节编号与流程步骤、阶段编号分别管理；不得因为章节为 `03` 就让内部阶段从 `03` 开始。
- 编号旁只保留一个中文栏目名和一个主标题。栏目名、主标题、数量标签不得重复表达同一含义。
- 数量标签仅在帮助扫描时保留，例如 `5 类场景`；如果标题已经写明“五类场景”，删除重复数量标签。

## 六、交付前进行三遍文案检查

1. **只读导航和标题**：不看正文也能说清项目主张、章节逻辑和下一步。
2. **清理元叙事**：搜索“表达、只用于、不替代、先确认、分开、决策门、maturity、gate、handoff、gotchas”等词，逐项判断是否泄露制作过程或内部术语。
3. **朗读检查**：把每个标题和章节说明读出声；如果像提示词、审稿意见、免责声明或英文直译，改成客户结论或具体行动。

普通说明句也应主语明确、动作清楚、逻辑完整。不要为显得谨慎而把一句话堆成多层限定，也不要让“本页、本节、材料、公开资料”长期充当段落主角。
